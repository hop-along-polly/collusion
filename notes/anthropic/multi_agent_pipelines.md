## Terminology

 - `Agent`: Models dynamically directing their process and tool usage. Best used for prompts where the goals are well-defined but the steps to getting to those goals is not.
 - `Workflow`: Models and tools orchestrated through predefined code paths. Best used when both the goals and steps to getting those goals are well-defined.
 - `Tool`: An executable function provided to a Model that the model can use to perform actions other than text generation.

## Building Effective Agents

There are **3 core principles** for implementing agents
 1. Keep it simple
 2. Prioritize transparency into your systems reasoning
 3. Thoroughly document and tests your Tools to ensure a intuitive and useful agent-computer interface (ACI)

## Mutli-Agent Design Patterns
| Pattern | Description | Use Cases |
| ------- | ----------- | --------- |
| `Prompt Chaining` | A design pattern where a task is decomposed into a sequence of steps where each step is handled by a different Model that processes the output of the step before it. | <ul><li>Task can be decomposed easily and cleanly into subtasks</li><li>Goal is to trade latency for higher accuracy</li></ul> |
| `Routing` | Classifing a task and routing it to a specialized workflow for handling that class of task. | <ul><li>Classification can be handled by a Model</li><li>Complex tasks with distinct sub-categories</li><li>Optomizing for one class of input hurts performance for the other classes of inputs</li></ul> |
| `Parallelization` (sectioning) | A variant of Parallelization where independent sub-tasks run in parallel | <ul><li>When divided subtasks can be run independently to improve speed</li></ul> | 
| `Parallelization` (voting) | A variant of Parallelization where the same task is run multiple times, sometimes using multiple Models, to get diverse outputs. | <ul><li>When multiple perspectives or attempts will increase condifence in results.</li></ul> | 
| `Orchestrator-Worker` | A Mutli-Agent design pattern that uses a Lead/Orchestrator Agent to decompose a task and delegate parts of that task to subagents. | <ul><li>Complex tasks where you can't predict the subtasks needed</li><li>The workflow needs to maximize flexibility.</li></ul> |
| `Evaluator-Optimizer` | Using a Model to evaluate the output from another Model and provides feedback in a loop | <ul><li>Tasks where clear evaluation criteria are present</li><li>Tasks where human feedback will improve the responses **AND** a Model can provide that feedback</li></ul> | 

## Prompt Engineering for Multi-Agent Systems

Multi-Agent systems are significantly more complex to orchestrate since each Agent is steered by
it's own prompt. This makes Prompt Engineering the primary lever for improving how well the
system functions. The following principles can be used to improve the coordination and
effectiveness of Multi-Agent Systems.

> [!NOTE]
> Anthropics prompting philosophy is to instill good heuristics instead of rigid rules.

1. `Observe and fine tune your agents thinking`: Run simulations using your exact System Prompt(s) so you can see how an Agent/Subagent thinks and what tools it calls. Use the observations from the simulation to write a System Prompt that guides the Agent towards calling the correct tools and away from bad thinking.
2. `Teach the Orchestrator how to delegate`: Define what the Orchestrator Agent should include when writing task definitions for the subagents it spawns. Common things to include are
  - A well defined objective
  - Structured output format
  - Guidance on the tools and sources to use
  - Clear task boundaries
3. `Embed Scaling Rules`: Include specific instructions on how many subagents and tool calls different types of user queries
should use. 

**Embedded Scaling Rules Example**
```
Classify the user query based on complexity and then use the following scaling rules when spinning up subagents for handling the user request.

 - Fact Finding: No more than 1 subagent and 3-10 tool calls.
 - Direct Comparison Analysis: 2-4 subagents each using 10-15 tool calls.
 - Complex Open Ended Research: 10+ subagents each with specific and clearly defined responsibilities. No 2 agents should research the same topic.
```
4. `Teach the Agent how to Evaluate Tools for Use`: Define a process and heuristics for evaluating which Tools the Agent should use. As the number of tools available to an Agent grows the harder it becomes for the Agent to chose the right tools. This is referred to as "Choice Paralysis", "Tool Overload" and getting "lost in the middle". The best way to avoid this is provide better tool descriptions, however when adding a 3rd party MCP you don't control the tool definition so providing heuristics and a process for evaluating tools in the System Prompt is your only method of improving tool use.
5. `Let Agents self improve`: Use a Model to analyze the Agents behaviours (reasoning, tool calling, etc.) and allow it to rewrite system prompts and tool descriptions to avoid failures.
6. `Start wide, then narrow down`: When implementing a Agent that performs research tasks it should start with a wide and shallow investigation of topics before it drills down into the specifics details.
7. `Enable Extended Thinking, and Interleaved Thinking`: The orchestrator model should enable Extended Thinking which allows the Model to generate additional tokens that explain it's thinking process. This improves the Models reasoning and instruction following. Interleaved Thinking should be enabled on subagents allowing them to reason between tool calls. This improves the subagents adaptability to new tasks.
8. `Parallelize tool calls`: Complex tasks can be handled quicker if multiple Subagents are run in parallel because each agent can call tools in parallel unlike a single agent which has to call tools sequentially.

> [!NOTE]
> Anthropic recommends prompting a Multi-Agent system with a framework for collaboration that defines the division of labor, problem solving approach and efort budget rather than strict instructions.


## Evaluating Multi-Agent Systems

**The Problem**
Agents are more difficult to evaluate than workflows because they chose their own path for handling a User Prompt (non-deterministic). Multi-Agent systems are even more difficult due to the non-deterministic nature of each individual Agent. Given the same input the Orchestrator Agent one time might spin up 3 subagents and the next time 10. Each subagent in turn might also use completely different tool calls to get to the same results.

### Best Practices for Evaluating Multi-Agent Systems

 - `Start early with small samples`: Create a small set of benchmark prompts early on during development to establish a base line for each Agent.
 - `Scale evaluations using a Model as the Judge`: Specify a rubric in the Judge Models System Prompt to ensure it makes its judgement on criteria that actually matter. 
 - `Humans evaluations are still necessary`: A Judge Model can miss hallucinations, system failures and biases in source selection. (e.g. Anthropics research agent would often chose SEO optimized content over more authoritative but less highly ranked sources)


> [!NOTE]
> Careful prompting, tool design, solid heuristics, observability, and tight feedback loops are essential for building quality System Prompts for a Multi-Agent system.

## Reliability and Engineering Challenges

Agents are non-deterministic and stateful which requires special consideration and techniques to ensure reliability at scale.
When engineering a Multi-Agent system follow these best practices.

1. `Make state durable`: Store message history somewhere external from the current Agent process so if there is a failure the Agent can restart where it left off. 
2. `Allow Agents to handle Tool errors`: A Model can understand and correct how it calls tools. All you need to do is specify how the Model knows the Tool failed.
3. `Setup full tracing and observability`: Build in Request Tracing and Observability including decision patterns, and interaction structures so you can see how a User Prompt was handled and where the system failed.
4. `Use Rainbow Deployments`: Rainbow deployments gradually phase out old Agents by shifting traffic from the old version of an Agent to the new version. New requests are always routed to the new version while existing requests continue to use the old version. When all the existing requests eventually burn down (complete, fail etc.) only then is the old version removed.
5. `Use Parallel Subagents`: Allow the main Agent to spin-up multiple subagents in parallel to improve the speed and efficiency of a Multi-Agent system. 

> [!NOTE]
> Parallel subagents requires more orchestration logic just like any parallel processing application.
